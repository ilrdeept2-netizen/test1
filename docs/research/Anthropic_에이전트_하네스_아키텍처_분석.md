# Anthropic 에이전트 하네스 아키텍처 분석

> Claude에게 '그럴듯한 결과'를 넘어, 스스로 설계·생성·검증까지 하게 만드는 하네스 구조 실험 정리

---

## 1. 하네스(Harness)란 무엇인가

### 정의

하네스는 AI 에이전트가 **장시간 자율적으로 작업을 수행할 수 있도록 감싸는 운영 구조**다. 단순히 프롬프트를 던지고 결과를 받는 것이 아니라, 에이전트의 작업 흐름 전체를 설계·제어·검증하는 프레임워크를 의미한다.

### 기존 방식과의 차이

| 구분 | 기존 프롬프트 엔지니어링 | 하네스 엔지니어링 |
|------|------------------------|------------------|
| **초점** | 입력(프롬프트) 최적화 | 작업 흐름 전체 설계 |
| **작업 시간** | 단발성 (1회 호출) | 장시간 (수 시간~수일) |
| **검증** | 사람이 결과 확인 | 에이전트가 스스로 검증 |
| **실패 처리** | 재시도 or 수동 개입 | 자동 복구·분기·재시도 |
| **상태 관리** | 없음 (stateless) | 컨텍스트 유지·압축·전달 |

핵심: 프롬프트 엔지니어링이 "무엇을 물어볼까"라면, 하네스 엔지니어링은 **"어떻게 끝까지 일하게 할까"**다.

## 2. Anthropic의 하네스 구조 실험 핵심

### 2.1 멀티스텝 자율 실행 (Multi-Step Autonomous Execution)

Anthropic이 실험한 하네스의 가장 큰 특징은 **에이전트가 하나의 큰 과제를 여러 단계로 나눠 스스로 실행**한다는 점이다.

```
[사용자 지시]
    ↓
[계획 수립 (Plan)] → 작업을 하위 태스크로 분해
    ↓
[실행 (Execute)] → 각 태스크를 순차/병렬 수행
    ↓
[검증 (Verify)] → 결과를 스스로 평가
    ↓
[보정 (Correct)] → 실패 시 재시도 또는 대안 탐색
    ↓
[완료 보고]
```

이 루프가 **사람의 개입 없이** 여러 시간 동안 반복된다.

### 2.2 컨텍스트 윈도우 관리 전략

장시간 작업에서 가장 큰 기술적 병목은 **컨텍스트 윈도우 한계**다. Anthropic의 하네스는 이를 다음과 같이 해결한다:

- **자동 압축(Auto-compression)**: 이전 대화를 요약하여 핵심만 유지
- **작업 상태 외부화**: 할 일 목록(Todo), 파일 시스템, Git 등에 상태를 기록
- **서브에이전트 위임**: 독립적인 탐색/연구 작업은 별도 에이전트에 위임하여 메인 컨텍스트 보호

```
[메인 에이전트 컨텍스트]
    ├── 핵심 지시사항 유지
    ├── 현재 진행 상태 (Todo)
    └── 서브에이전트 결과 요약만 수신
        ├── [탐색 에이전트] → 코드베이스 조사
        ├── [계획 에이전트] → 구현 설계
        └── [검증 에이전트] → 테스트 실행
```

### 2.3 도구 사용 패턴 (Tool Use Patterns)

하네스의 핵심은 에이전트가 **적절한 도구를 적절한 시점에 선택**하도록 유도하는 것이다.

Anthropic이 설계한 도구 체계:

| 도구 범주 | 역할 | 예시 |
|-----------|------|------|
| **읽기 도구** | 정보 수집 | Read, Grep, Glob |
| **쓰기 도구** | 코드/문서 생성 | Write, Edit |
| **실행 도구** | 명령 실행·검증 | Bash, 테스트 러너 |
| **관리 도구** | 작업 추적·계획 | TodoWrite, Agent |
| **외부 연동** | 서비스 통합 | MCP 서버, GitHub API |

중요한 원칙:
- **전용 도구 우선**: `cat` 대신 `Read`, `grep` 대신 `Grep` 사용
- **병렬 실행**: 독립적인 도구 호출은 동시에 실행
- **최소 권한**: 위험한 작업은 사용자 확인 후 실행

### 2.4 실패 복구 메커니즘

장시간 작업에서 실패는 필연적이다. 하네스는 이를 **시스템 수준에서** 처리한다:

```
실패 발생
    ↓
[1단계] 원인 분석 — 에러 메시지, 로그 확인
    ↓
[2단계] 대안 탐색 — 다른 접근법 시도
    ↓
[3단계] 범위 축소 — 문제를 더 작은 단위로 분리
    ↓
[4단계] 사용자 질의 — 위 모든 시도 실패 시에만 개입 요청
```

**브루트포스 금지 원칙**: 같은 실패를 반복 재시도하지 않는다. 실패하면 반드시 접근법을 바꾼다.

## 3. 하네스의 운영 설계 원칙

### 3.1 점진적 자율성 (Progressive Autonomy)

모든 작업을 에이전트에게 한번에 맡기지 않는다. 위험도에 따라 자율성 수준을 조절한다:

| 위험도 | 자율성 수준 | 예시 |
|--------|-----------|------|
| 낮음 | 자동 실행 | 파일 읽기, 코드 검색 |
| 중간 | 실행 후 보고 | 파일 수정, 테스트 실행 |
| 높음 | 사전 확인 필수 | Git push, PR 생성, 삭제 |
| 매우 높음 | 명시적 승인 필요 | Force push, DB 변경, 프로덕션 배포 |

### 3.2 외부 상태 의존 (External State Dependency)

에이전트의 "기억"을 컨텍스트 윈도우에만 의존하지 않는다:

- **파일 시스템** = 장기 기억 (코드, 문서, 설정)
- **Git** = 버전 관리된 기억 (변경 이력, 브랜치)
- **Todo 리스트** = 작업 기억 (현재 진행 상태)
- **MCP 서버** = 외부 서비스 기억 (GitHub, Slack 등)

이를 통해 컨텍스트가 압축되더라도 **핵심 상태는 보존**된다.

### 3.3 서브에이전트 아키텍처

하나의 에이전트가 모든 것을 처리하지 않는다. 역할별로 전문화된 서브에이전트를 활용한다:

```
[메인 에이전트 (오케스트레이터)]
    │
    ├── [Explore 에이전트] — 코드베이스 탐색 전문
    │   빠른 파일 검색, 키워드 탐색, 구조 파악
    │
    ├── [Plan 에이전트] — 설계 전문
    │   구현 계획 수립, 아키텍처 설계, 트레이드오프 분석
    │
    ├── [General Purpose 에이전트] — 복잡한 멀티스텝 작업
    │   연구, 코드 검색, 다단계 작업 실행
    │
    └── [특수 에이전트] — 특정 도메인
        테스트 실행, 빌드 검증, 설정 관리
```

서브에이전트의 핵심 가치:
1. **컨텍스트 격리**: 메인 에이전트의 컨텍스트를 오염시키지 않음
2. **병렬 실행**: 독립적인 작업을 동시 수행
3. **실패 격리**: 서브에이전트 실패가 메인에 전파되지 않음

## 4. 실전에서의 하네스 패턴

### 4.1 코드 구현 하네스

```
1. 요구사항 분석 → Plan 에이전트로 설계
2. 기존 코드 탐색 → Explore 에이전트로 구조 파악
3. 구현 → 메인 에이전트가 코드 작성
4. 테스트 → Bash로 테스트 실행, 실패 시 자동 수정
5. 커밋 → Git으로 상태 저장
6. PR 생성 → GitHub MCP로 리뷰 요청
7. CI 모니터링 → PR 활동 구독으로 자동 대응
```

### 4.2 디버깅 하네스

```
1. 버그 리포트 수신 → 이슈 내용 분석
2. 관련 코드 탐색 → Grep/Glob으로 범위 좁히기
3. 가설 수립 → 원인 후보 목록 작성
4. 가설 검증 → 테스트 작성·실행
5. 수정 적용 → 최소 변경 원칙
6. 회귀 테스트 → 기존 테스트 전체 실행
7. 결과 보고 → PR + 설명
```

### 4.3 장시간 연구 하네스

```
1. 주제 정의 → 사용자 지시 파싱
2. 정보 수집 → 웹 검색 + 코드 분석 (서브에이전트 병렬)
3. 중간 정리 → 파일에 중간 결과 저장 (컨텍스트 보호)
4. 심층 분석 → 수집된 정보 기반 추론
5. 문서화 → 구조화된 문서 작성
6. 자체 검증 → 논리적 일관성, 출처 확인
```

## 5. 하네스 엔지니어링이 중요한 이유

### 5.1 프롬프트의 한계를 넘어서

아무리 정교한 프롬프트를 작성해도, 단일 호출로는 복잡한 실무 작업을 완수할 수 없다. 하네스는 **"좋은 질문"이 아니라 "좋은 작업 환경"**을 만드는 것이다.

### 5.2 에이전트 시대의 운영 패러다임

| 시대 | 핵심 역량 | 비유 |
|------|----------|------|
| 검색 시대 | 검색어 작성 | 도서관에서 책 찾기 |
| 프롬프트 시대 | 프롬프트 작성 | 전문가에게 질문하기 |
| **하네스 시대** | **작업 환경 설계** | **팀을 구성하고 프로세스 만들기** |

하네스 엔지니어링은 단순히 AI를 "잘 쓰는" 것이 아니라, AI가 **자율적으로 일할 수 있는 구조를 설계**하는 것이다. 이는 소프트웨어 엔지니어링의 DevOps가 그랬듯, **운영(Operations)의 관점**에서 AI 활용을 바라보는 전환점이다.

### 5.3 핵심 시사점

1. **컨텍스트 관리가 곧 성능이다** — 모델 능력보다 컨텍스트를 얼마나 효율적으로 관리하느냐가 결과 품질을 결정
2. **도구 설계가 곧 역량이다** — 에이전트에게 어떤 도구를 어떻게 주느냐가 할 수 있는 일의 범위를 결정
3. **실패 설계가 곧 신뢰다** — 실패를 어떻게 처리하느냐가 장시간 자율 운영의 신뢰도를 결정
4. **자율성은 점진적으로** — 모든 것을 한번에 자동화하지 않고, 위험도에 따라 자율성 수준을 조절

---

## 6. 결론

Anthropic의 하네스 구조 실험은 겉으로는 에이전트 실험처럼 보이지만, 본질은 **"AI를 장시간 신뢰할 수 있게 만드는 운영 설계"**다.

프롬프트 엔지니어링이 "한 번의 대화를 최적화"하는 것이었다면, 하네스 엔지니어링은 **"연속된 작업 흐름 전체를 최적화"**하는 것이다.

이것이 의미하는 바는 명확하다:

> **AI 활용의 다음 단계는 "더 똑똑한 모델"이 아니라, "더 나은 작업 구조"에서 온다.**

모델이 아무리 좋아져도, 그것을 감싸는 하네스가 부실하면 실무에서 쓸 수 없다. 반대로, 하네스가 잘 설계되어 있으면 현재 모델로도 놀라운 수준의 자율 작업이 가능하다.
