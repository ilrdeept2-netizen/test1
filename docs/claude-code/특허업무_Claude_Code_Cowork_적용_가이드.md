# 특허업무 방식 분석 및 Claude Code/Cowork 적용 가이드

> 본 리포지토리에 축적된 특허업무 자산을 분석하고, Claude Code와 Cowork에서 실전 적용하는 방법을 정리한 가이드

---

## 1. 현재 보유 자산 분석

### 1.1 특허업무 도구 (3종)

| 도구 | 파일 | 역할 |
|------|------|------|
| **특허 문서 변환기** | `patent_format_converter.py` | Word/HWP/PDF → KIPO HLT(XML) 변환 |
| **선행특허조사 앱** | `patent_search_app.py`, `patent_search_web.py` | 문서→키워드 추출→KIPRIS API 검색 |
| **명세서 작성 AI 가이드** | `patent_specification_guide.md` | 도면~청구항~OA까지 단계별 프롬프트 템플릿 |

### 1.2 업무 가이드 문서 (3종)

| 문서 | 핵심 내용 |
|------|-----------|
| `Claude_Cowork_리걸플러그인_특허업무_활용_고찰.md` | Legal 플러그인 패턴→특허업무 차용 전략, Skills/MCP/Hooks/Plugins 확장 체계 |
| `플러그인_정리_및_특허업무_활용가이드.md` | 도구별 활용도 정리, 7가지 추천 프롬프트 세트, End-to-End 워크플로우 |
| `Claude_Cowork_특허업무_프롬프트_가이드.md` | 11개 업무 카테고리×50+ 프롬프트 템플릿, 실전 워크플로우 예시 |

### 1.3 업무 방식의 핵심 패턴

분석 결과, 3가지 핵심 패턴이 관통합니다:

1. **단계 분리형 워크플로우** — 발명 분석 → 선행조사 → 도면 → 명세서 → 청구항 → 검토를 세션 단위로 분리
2. **서술 원칙 사전 주입** — 간결체 4원칙(접속사 삭제, 지시어 최소화, 단문 위주, 능동태)을 세션 시작 시 설정
3. **신호등 시스템 차용** — Legal 플러그인의 🟢🟡🔴 패턴을 청구항 강도, OA 보정 난이도 등에 적용

## 2. Claude Code에서 적용하는 법

### 2.1 Skills (커스텀 슬래시 커맨드) — 가장 실용적

`.claude/skills/` 디렉토리에 SKILL.md 파일을 만들면 `/명령어`로 호출 가능합니다.

#### 예시 1: `/check-spec` — 명세서 기재불비 점검

```markdown
<!-- 파일: .claude/skills/check-spec/SKILL.md -->
---
name: check-spec
description: 특허 명세서 기재불비 자동 점검
user-invocable: true
allowed-tools: Read, Grep, Glob, Bash
---

업로드된 특허 명세서를 읽고 다음 기준으로 기재불비를 점검하세요.

## 점검 항목

### 필수 섹션 (누락 시 🔴)
- 【발명의 명칭】, 【기술분야】, 【발명의 배경이 되는 기술】
- 【해결하고자 하는 과제】, 【과제의 해결 수단】, 【발명의 효과】
- 【도면의 간단한 설명】, 【발명을 실시하기 위한 구체적인 내용】
- 【청구범위】

### 서술 원칙 위반 (항목별 🟢🟡🔴)
- 접속사('또한', '그리고', '나아가') 사용 여부
- 지시어('상기', '본', '해당') 과다 사용 여부
- 수동태 문장 비율
- 만연체(복합문) 비율

### 정합성 (항목별 🟢🟡🔴)
- 청구항 구성요소가 명세서 본문에 모두 기재되어 있는지
- 부호번호가 청구항↔명세서↔도면 간 일치하는지
- 용어가 문서 전체에서 통일되어 있는지

## 출력 형식
| # | 점검항목 | 상태 | 상세 |
형식의 표로 결과를 정리하고, 🔴 항목에 대해 수정 제안을 제시하세요.
```

#### 예시 2: `/review-oa` — OA 분석 및 대응

```markdown
<!-- 파일: .claude/skills/review-oa/SKILL.md -->
---
name: review-oa
description: OA(의견제출통지서) 분석 및 대응안 생성
user-invocable: true
allowed-tools: Read, Grep, Glob, Bash, Write
---

당신은 출원인의 권리범위 극대화와 등록 사이의 트레이드오프를 짚어내는
한국 특허 실무 전문가입니다.

## 4대 핵심 원칙
1. 청구항은 객관적 구조로만 한정 (기능/효과/수치 기재 금지)
2. 효과와 기작은 의견서에서 진보성 주장의 무기로 활용
3. 관련 출원과 권리범위 중복 회피
4. 신규사항 추가 원천 차단 (명세서 원문 워딩 그대로 차용)

## 분석 절차

### 1단계: 거절이유 분석
- 거절이유 유형 분류 (신규성/진보성/기재불비/산업상이용가능성)
- 인용발명 관련성 평가
- 심사관 논리의 취약점 식별

### 2단계: 대응 난이도 평가 (신호등)
- 🟢 단순 보정으로 극복 가능
- 🟡 실질적 보정 필요, 극복 가능성 있음
- 🔴 보정으로 극복 곤란 — 분할출원/포기 검토 필요

### 3단계: 보정안 + 의견서 초안
- 보정된 청구항 1항 (4대 원칙 준수)
- 인용발명 대비 구성요소별 비교표
- 진보성 논증: 구성 차이→작용효과 차이 순서

결과를 OA_대응안.md 파일로 저장하세요.
```

#### 예시 3: `/draft-claims` — 청구항 초안

```markdown
<!-- 파일: .claude/skills/draft-claims/SKILL.md -->
---
name: draft-claims
description: 명세서 기반 청구항 초안 작성
user-invocable: true
allowed-tools: Read, Write
---

명세서 본문과 부호체계를 읽고 청구항을 작성하세요.

## 작성 원칙
- 독립항 1항: 권리범위 최대 확보
  → 객관적 구조(물리적 배치, 결합 관계)로만 한정
  → 기능/효과/수치 기재 금지
- 종속항: 개별 특징을 각 1개씩 한정 (5~7개)
- 카테고리: 장치/방법/시스템 중 적합한 것 선택

## 출력
- 청구항.md 파일로 저장
- 각 청구항 아래에 [근거: 명세서 해당 단락] 주석 추가
```

### 2.2 MCP 서버 연동 — 외부 데이터 접근

```bash
# KIPRIS API 연동 (선행기술 실시간 조사)
claude mcp add --transport http kipris https://your-kipris-mcp-server.com/mcp

# SQLite — 자체 특허 DB 관리 (포트폴리오, 기한 관리)
claude mcp add --transport stdio patent-db -- npx -y @bytebase/dbhub --dsn "sqlite:///patents.db"

# Notion — 특허 업무 보드 연동
claude mcp add --transport http notion https://mcp.notion.com/mcp

# Slack — 발명자/담당자 커뮤니케이션
claude mcp add --transport http slack https://mcp.slack.com/mcp
```

### 2.3 Hooks — 이벤트 기반 자동화

```json
// .claude/settings.json
{
  "hooks": {
    "on-file-change": [
      {
        "pattern": "drafts/**/*.md",
        "command": "echo '명세서 파일이 변경되었습니다. /check-spec 으로 기재불비 점검을 권장합니다.'"
      }
    ]
  }
}
```

### 2.4 Agent Teams — 병렬 처리

```
다음 3가지 작업을 에이전트 팀으로 병렬 수행해줘:

팀원A — 선행기술 조사:
  발명설명서.docx 기반 KIPRIS 유사 특허 검색 및 분석

팀원B — 청구항 초안:
  핵심 기술 파악 → 독립항 1개 + 종속항 5~7개

팀원C — 도면 계획 및 부호체계:
  도면 5~6장 계획 + 부호체계 초안

결과를 종합하여 명세서 작성 방향을 정리해줘.
```

## 3. Claude Cowork에서 적용하는 법

Cowork은 로컬 파일을 직접 읽고 편집할 수 있는 데스크톱 에이전트입니다.
Claude Code의 모든 기능에 더해 **GUI 기반 파일 탐색과 직접 편집**이 추가됩니다.

### 3.1 Cowork 특화 활용법

| 시나리오 | Cowork 활용 |
|---------|-------------|
| **명세서 직접 편집** | 로컬 docx/md 파일을 열어서 서술 원칙 위반 사항 자동 수정 |
| **도면 HTML 생성→확인** | HTML 도면 코드 생성 후 즉시 로컬에서 렌더링 확인 |
| **OA 문서 분석** | PDF 파일을 직접 읽어서 거절이유 분석 + 대응안 작성 |
| **포트폴리오 관리** | 로컬 스프레드시트/DB 연동으로 기한 관리 |

### 3.2 Cowork 프롬프트 예시 — 명세서 자동 수정

```
내 문서 폴더(~/Documents/Patents/2026-001/)에 접근해서:
1. 명세서_초안.docx를 읽고 기재불비 사항을 점검해줘.
2. 다음 항목을 자동으로 수정해줘:
   - '상기' → 해당 구성요소명+도면번호로 교체
   - 접속사(또한, 그리고, 나아가) 삭제
   - 수동태 → 능동태 변환
3. 수정된 파일을 명세서_수정.docx로 저장해줘.
```

### 3.3 Legal 플러그인 패턴 차용

Legal 플러그인에 특허 기능은 없지만, 그 접근 방식을 Skills로 재현할 수 있습니다:

| Legal 플러그인 패턴 | 특허업무 적용 | 구현 방식 |
|---------------------|-------------|-----------|
| 계약서 신호등 (🟢🟡🔴) | 청구항 강도 평가, OA 보정 난이도 | `/check-spec`, `/review-oa` Skill |
| 플레이북 기반 분석 | KIPO 심사기준 기반 명세서 점검 | Skill + 레퍼런스 파일 |
| 레드라인 제안 | 보정안 자동 생성 | `/review-oa` Skill |
| NDA 분류 | 특허 문서 자동 분류 | `/triage-invention` Skill |
| Pramata Extension | KIPRIS 연동 | MCP 서버 |

## 4. 실전 워크플로우 — End-to-End

### 4.1 신규 출원 워크플로우

```
┌──────────────────────────────────────────────────────────────┐
│              신규 출원 End-to-End 워크플로우                     │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  [세션 1] 발명 분석                                           │
│   ├── 발명설명서 초기 분석 (기술분야, 과제, 차별점)            │
│   ├── 발명자 질문 목록 생성                                   │
│   └── 선행기술 검색 키워드 도출                                │
│                                                              │
│  [세션 2] 선행기술 조사                                       │

│   ├── 선행문헌 비교 분석 (구성요소별 대비표)                   │

│  [세션 3] 도면 + 부호체계                                     │
│   ├── 서술 스타일 사전 설정 (간결체 4원칙)                    │
│   ├── 도면 계획 수립 (5~7장)                                  │
│   ├── HTML 도면 생성 (무채색 특허 스타일)                      │
│   └── 부호체계 최종 정리                                      │
│                                                              │

│   ├── 명세서 항목 일괄 작성                                   │

│   └── 인과관계 강화 (베테랑 변리사 모드)                      │
│                                                              │
│  [세션 5] 청구항 + 최종 검토                                  │
│   ├── /draft-claims — 청구항 초안                              │
│   ├── 청구항 권리범위 검토                                    │
│   ├── /check-spec — 기재불비 점검                              │
│   ├── 정합성 크로스체크                                       │
│   └── patent_format_converter.py → HLT 변환                   │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 4.2 OA 대응 워크플로우

```
[세션 1] /review-oa 실행
  ├── OA 문서 + 인용문헌 + 출원명세서 업로드
  ├── 거절이유 유형 분류 및 정당성 검토
  ├── 대응 난이도 평가 (🟢🟡🔴)
  └── OA_분석.md 생성

[세션 2] 보정서/의견서 작성
  ├── 보정된 청구항 1항 (4대 원칙 준수)
  ├── 인용발명 대비 구성요소별 비교표
  ├── 진보성 논증 (구성 차이→작용효과 차이)
  ├── 보정 전후 비교표 (볼드/취소선)
  └── 보정서_의견서.md 생성

[세션 3] 최종 검토
  ├── 신규사항 추가 여부 점검
  └── 보정 후 명세서 정합성 확인
```

### 4.3 빈출 단발성 업무 — 즉시 사용 가능 프롬프트

| 업무 | 프롬프트 |
|------|---------|
| **요약서** | `청구항.md의 독립항 1항을 기초로 요약서를 400자 이내로 작성해줘` |
| **발명의 명칭** | `명세서_최종.md를 읽고 발명의 명칭 후보 5개를 제안해줘. 20자 이내` |
| **IPC 분류** | `명세서 기술 내용을 분석해서 IPC 주분류 1개 + 부분류 3개 추천해줘` |
| **PCT 요약서** | `specification_EN.md 기초로 PCT Abstract를 150 words 이내로 작성해줘` |
| **HLT 변환** | `patent_format_converter.py로 명세서_최종.docx를 HLT로 변환해줘` |
| **한→영 번역** | `명세서_최종.md를 특허 번역 용어집 적용하여 영문 번역해줘` |
